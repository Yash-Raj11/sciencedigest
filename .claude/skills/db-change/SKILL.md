# Database change

Ask the owner before changing a table's shape, what scoring means, or anything that touches
stored user history (`step_checkins`, `step_amounts`, `equipped_protocols`,
`user_program_state`). These are expensive to undo.

## Rules

1. **New dated migrations only.** Never edit a migration that is already live; add
   `supabase/migrations/<yyyymmddhhmmss>_<name>.sql`. `supabase/seed.sql` is generated by
   `npm run content:build`; never edit it.
2. **Every test must hold whatever data exists**: the seeded pass and its background users,
   production included. Count what the rule says must be visible, then compare; never compare a
   whole table against the test's own fixtures. Exact-row comparisons only on fixture rows.
   Every test file is `begin ... rollback`.
3. **A mutation for every new rule.** Add a case to `scripts/db-mutation-test.sh` that breaks
   the rule, and show a test catching it.
4. **Scoring changes go in TypeScript and SQL together**: `lib/score.ts` and
   `compute_adherence()`; weights in `lib/evidence.ts` and `evidence_weight()`. Then
   `npm run parity:gen` (never edit `90_parity.generated.test.sql` by hand).
5. **No stored scores.** No `score`, `points`, `streak` or `percentage` column, ever.

## Before calling a SQL change done

```
npm run db:test:local     # both passes must print 0 failed: unseeded, then seeded
npm run db:mutation       # survived: 0
npm run lint && npm run typecheck && npm test && npm run build
```

Paste the real output. Save it to `docs/evidence/database-tests.txt` and
`docs/evidence/mutation-tests.txt`.

**Never point `npm run db:test:local` at a Supabase database.** Its shim creates, and its
cleanup drops, the `anon`, `authenticated` and `service_role` roles.

## Hosted changes (project `takhienzcshgkytbvaii`)

On Supabase CLI 3.x every command targets local Docker unless `--remote` is given.

1. `supabase db push --remote --dry-run --include-seed` and show the owner what would change.
2. **Ask before the real push.** Only after a yes: `supabase db push --remote --include-seed --yes`.
   On a project that is already seeded this applies migrations but **does not re-run a changed
   seed** (it prints "Updating seed hash" and writes no rows). When `supabase/seed.sql` changed,
   follow it with `supabase db query --remote --yes -f supabase/seed.sql` (idempotent upserts of
   reference content only; `scripts/seed-safety.test.ts` holds that), then count the rows.
3. Reads for evidence: `supabase db query --remote --read-only "<sql>"`. Counts and times only,
   no ids in the output.

An assistant session never holds the service role key or the database password.

## Running the tests against the hosted project

`supabase test db --remote` needs Docker on this CLI, so:

1. Ask the owner, then install pgTAP for the run:
   `supabase db query --remote --yes "create extension if not exists pgtap with schema extensions"`
2. The owner runs the psql wrapper in their own Terminal (the password is typed at psql's
   prompt and never stored):
   ```
   for f in supabase/tests/database/*.test.sql; do
     echo "# $f"; psql "<connection string, no password>" -X -q -A -t -v ON_ERROR_STOP=1 -f "$f"
   done
   ```
   Every plan must complete with no `not ok` line.
3. Drop pgTAP and show it is gone:
   `supabase db query --remote --yes "drop extension pgtap"`, then
   `supabase db query --remote --read-only "select count(*) from pg_extension where extname = 'pgtap'"`
   must return 0.
